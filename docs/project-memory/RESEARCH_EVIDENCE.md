## Research use rules

1. Record the source publisher, page/version, publication date when available, and date checked.
2. Prefer the source's primary technical reference over blogs or search snippets.
3. Separate a vendor's documented behavior from TACResQ's implementation and from any operational conclusion.
4. For safety-critical claims, seek independent corroboration and clearly state uncertainty.
5. Re-check terms, pricing, API limits, platform policies, and versioned docs before enabling a provider or changing production behavior.
6. Do not use marketing claims as evidence of route safety, delivery guarantees, response times, or emergency-service suitability.

## Key synthesis

The most important cross-source conclusion is that TACResQ must be designed for partial failure: Android background work and location are scheduled/throttled; FCM is not a life-critical delivery channel; routing depends on provider data and configuration; and privileged database functions require explicit identity, role, and object checks in addition to a fixed search path. The app's persistent server records, safe retry identities, visible uncertainty, and manual fallbacks are therefore more important than optimistic claims of real-time behavior.
