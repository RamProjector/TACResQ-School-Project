# Admin account suspension: preliminary authorization-surface inventory

**Branch:** security/admin-account-suspension  
**Status:** source inventory plus first database foundation; NOT an exhaustive release checklist and NOT proof of runtime suspension. Migration `20261125020819_account_lifecycle_foundation.sql` adds default-active profile lifecycle fields, an append-only audit ledger, and `private.tacresq_current_account_active()`. Direct authenticated access to public RLS-enabled tables with table- or column-level client grants is now guarded by a restrictive policy. SECURITY DEFINER/invoker RPCs, Storage, Edge Functions, and bridge routes remain unguarded; no account has been suspended and no connected project was modified.

This inventory is intentionally conservative. A path is not marked covered merely because it checks a role or because it uses RLS. Suspension requires an independent current-account-state check. Each row remains **not yet guarded** until an implementation and negative test prove that a suspended caller is rejected.

## Implemented foundation and current limitation\n\n- Existing profiles are backfilled by the column default to `account_status = 'active'`; no current user is changed to suspended.\n- `private.tacresq_current_account_active()` reads and share-locks the current profile row for `auth.uid()` and returns false for missing/suspended profiles. A future transition RPC must use `FOR UPDATE` on the same row to establish the transaction boundary. It is granted to `authenticated` and is used by `tacresq_active_account_required`, a restrictive `FOR ALL` policy installed on each RLS-enabled public table with direct authenticated table/column privileges.\n- `account_lifecycle_audit_logs` is RLS-enabled, has no client/service-role table or sequence grants, and rejects UPDATE/DELETE through a trigger. A later trusted RPC must insert the event and update profile state in one transaction.\n- Lifecycle columns are not directly updateable by `authenticated`; there is intentionally no suspension RPC, Storage policy change, Admin UI, or session-revocation claim in this slice. A clean-replay assertion checks that every public table with direct authenticated grants has the restrictive policy.\n- The helper adds one authenticated-callable private SECURITY DEFINER function to the callable inventory; include it in the next clean-replay private-definer baseline.\n\n## Confirmed entry-point groups

## RLS and privilege evidence that changes the implementation plan

- The clean migration replay for this branch reports 23 authenticated-callable public SECURITY DEFINER functions (74 authenticated-callable public functions total). See [the clean-replay authorization snapshot](admin-account-suspension-clean-replay-snapshot.md) for the exact signatures and [RPC review batch 1](admin-account-suspension-rpc-review-batch-1.md) for source-traced account-state gaps. This isolated replay count supersedes the older 18-function preliminary review; it is not a live connected-project catalog.
- Five RLS-enabled operational tables were reviewed as intentionally having no direct client policies/grants: fcm_delivery_attempts, incident_messages, incident_request_edit_logs, incident_submission_keys, and user_notifications. Their RPCs/server writers still need caller-state checks.
- The five device/session registry tables (user_devices, device_sessions, device_challenges, device_security_events, device_integrity_checks) also have RLS enabled and no direct client table or sequence privileges. Their future service-role verifier paths remain a separate trust boundary; no client-facing verifier is assumed to exist.
- Some policies use private.tacresq_actor_role(); others resolve ownership by directly selecting profiles for auth.uid(). Updating the role helper alone is insufficient. The new `private.tacresq_current_account_active()` helper is called by restrictive direct-table RLS policies. Existing RPCs still require explicit guards because SECURITY DEFINER functions can bypass RLS.
- SECURITY DEFINER functions may bypass ordinary RLS. Each callable definer function needs a current-state guard inside its trusted body.
- Supabase Storage authorization is separate from ordinary Postgres table RLS. The current source inventory contains one application bucket (`incident-chat-attachments`); its SQL replay runs a read-only inventory contract that rejects unreviewed buckets, verifies the private bucket size/MIME settings and both reviewed object policies, and fails closed if an additional permissive `storage.objects` policy applies to PUBLIC or authenticated callers. The metadata-only summary safely aggregates numeric object-size metadata and does not print object paths or signed URLs. Any future bucket or client-facing permissive policy must be added to the inventory and receive bucket-specific authorization and suspended-session tests before release.
- The Laravel bridge is not the universal request path. Android and the web dashboard call Supabase directly, so Laravel middleware cannot provide complete suspension enforcement.

## Decision

Do not add the Suspend/Reactivate button yet. A UI control before complete server-side enforcement would create a false security promise. Continue with exact migration/catalog inventory and a testable enforcement design first.

## Anonymous routine exposure inventory

The read-only PostgreSQL catalog now reports effective anon EXECUTE access separately for routines in both public and private schemas. This is necessary because the authenticated-callable list does not by itself describe the anonymous role's effective grants. Results include routine owner, execution mode, configured search path, and whether authenticated also has EXECUTE.

Do not assume that an anon-callable routine is automatically a vulnerability: classify its intended unauthenticated use and trace its body and nested calls. Conversely, do not treat an empty source assertion as evidence that the replayed database has no anon-callable routines. Run the catalog against the clean replay and review every returned signature before enabling account transitions.

The Admin transition routine `public.api_admin_set_account_status(bigint,text,text)` remains staged with client EXECUTE revoked. It is a SECURITY DEFINER implementation, but it is not part of the authenticated-callable inventory or the 74-function public callable baseline until an explicit client grant is approved.
