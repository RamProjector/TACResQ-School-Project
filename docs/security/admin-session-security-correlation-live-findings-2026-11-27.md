## Executive finding

The Admin correlation UI was not the only problem. The live database currently has very little event data in the sources used by the Admin investigation feed. Supabase Auth is emitting audit events into the external log stream, but the database table queried by the feed is empty. The device-security event table is also empty, and the repository's trusted device-security event writer is not implemented.

As a result, adding correlation fields or search controls alone cannot make absent source records appear. The Admin UI must distinguish an empty persisted source from a complete security-event stream.

## Why the Admin sources are empty or uncorrelated

1. **Supabase Auth audit persistence:** provider audit events are visible in the external `auth_audit_logs` stream, but `auth.audit_log_entries` contains zero rows. The current dashboard setting for database persistence was not changed or independently confirmed. Supabase documents a setting named **Disable writing auth audit logs to project database** under Authentication → Audit Logs. If enabled, provider events remain in external logs but are not queryable through the database feed. Enabling database persistence affects future events; it does not backfill prior events.
2. **Device-security events:** `device_security_events` has no live rows. The private registry schema exists, but there is no trusted challenge verifier/device-event writer yet. The UI must not present this as a working alert producer.
3. **Laravel API-operation audit:** `api_operation_logs` has no live rows. The web client currently calls Supabase directly; the optional Laravel bridge is additive and its Admin session/investigation RPCs are not currently the browser's request path.
4. **App-action audit:** `app_action_audit_logs` has no live rows in the observed project snapshot. Do not infer that all application actions are covered.
5. **Incident and assignment sources:** status and request-edit history contain a small number of rows; assignment and claimability sources are empty in this snapshot. The feed is not a complete incident-operation timeline.

## Correlation semantics

Keep these identifiers distinct:

- **Auth session ID:** identity-provider session reference. It links events only when a trusted source records the verified JWT `session_id`.
- **W3C trace ID:** distributed request trace reference. It is observability metadata, not identity or authorization.
- **Application correlation ID:** server-generated request/transaction correlation. Do not trust caller-supplied values as authoritative.
- **Provider request ID:** upstream request identifier returned by Supabase. It identifies one provider request, not a user session.

A Supabase Auth audit event's provider request ID can help locate the corresponding provider request in logs. It must not be relabeled as a session ID. A trace ID generated independently for each browser request does not automatically correlate separate requests in a multi-step user flow.

## Follow-up: cross-source search behavior and migration readiness

A subsequent source review found a UI-level reason that correlation searches could appear incomplete: the **Find related** actions replaced the query text but retained the current source, category, date, actor, target, and incident filters. A prior filter could therefore hide events from another source even when they shared the selected technical reference.

The branch now routes all four technical-reference actions (Auth session ID, W3C trace ID, Laravel correlation ID, and Supabase provider request ID) through one helper that clears those prior filters before searching across the full investigation feed. The existing Python contract now asserts each reference action and each filter reset.

The session-inventory and investigation RPC clients also now convert PostgREST's missing-function/schema-cache response (PGRST202) into explicit migration-readiness messages rather than a generic unexpected-service error. These messages do not attempt to apply migrations or refresh the hosted schema.

A fresh read-only query of the connected Supabase migration ledger confirmed:
- Latest applied migration: `20261125030354`
- Admin session-inventory migration `20261127020000`: not applied
- Admin trace-correlation migration `20261127080000`: not applied

Therefore, the branch's session inventory and new correlation projection are **not yet available in the hosted project**. A green local replay is not evidence of hosted deployment. The Admin portal and database migration must be released together after the project's operator authorizes deployment.
