# Location reader freshness and access review

## Scope

Review the database boundary for responder location writes and dispatcher location reads, with emphasis on access control, timestamp trust, and emergency-operation reliability.

This is a repository-source review. It does not query the live database, inspect the deployed Storage policies, or change runtime behavior.

## Access-control findings

### Location writes

The current `api_record_location_v2` public function is a SECURITY INVOKER wrapper around the private `private.tacresq_record_location_v2` SECURITY DEFINER implementation.

The private writer:

- Derives the actor profile from `auth.uid()`; it does not accept a client-selected profile ID.
- Requires a responder/driver profile with a matching assignment to the incident.
- Requires both the incident and that unit's assignment status to be `en_route`.
- Validates latitude, longitude, accuracy, and the client capture timestamp bounds.
- Locks the incident and assignment rows, then serializes writes by actor before applying an eight-second interval limit.
- Inserts through the private helper after direct authenticated INSERT on `location_logs` has been revoked.
- Uses server-generated `received_at` separately from client-supplied `recorded_at`.

The public wrapper and private implementation have explicit authenticated execute grants; anonymous/public execution is revoked in the reviewed migration.

### Location reads

The current `api_active_responder_locations` public RPC delegates to a private SECURITY DEFINER helper. The helper checks that the caller's current profile role is dispatcher before reading location rows. It returns only the latest eligible point per incident/unit and limits results to incidents and individual assignments that are both `en_route`.

The query validates coordinate ranges and non-negative accuracy, and the current helper limits the result to points whose `recorded_at` is within the previous two minutes. The helper has explicit execute grants and the public wrapper is invoker-security.

The reviewed boundary does not show an obvious route for requesters, responders, drivers, or Admin accounts to use this dispatcher location reader successfully. This conclusion is limited to the reviewed source definitions and grants; it is not a live catalog verification.

## Finding: freshness uses a client-controlled timestamp

The writer accepts `p_recorded_at` from the device, defaulting it to database time only when omitted. It permits capture timestamps up to 15 minutes old and up to five minutes in the future. It stores a separate server receipt timestamp in `received_at`.

The location reader orders candidate points by `COALESCE(received_at, recorded_at)`, correctly preferring server receipt time for ordering. However, its two-minute freshness filter is based on `recorded_at`, the device-reported capture time.

This mixes two different meanings:

- `recorded_at`: when the device says the location was captured; useful for diagnosing delayed capture and displaying capture age.
- `received_at`: when the database accepted the point; generated by the server and suitable for measuring ingestion recency and rate limiting.

A point can be accepted by the server now, have a valid assignment and coordinates, and still be excluded from the dispatcher's active-location response because its device capture timestamp is older than two minutes. A device clock that is behind can therefore make a freshly received point disappear from the live map. Conversely, relying only on server receipt time can make a delayed, old capture look newly received unless the client capture age remains visible.

This is a freshness/availability semantic mismatch, not proof of an access-control bypass.

## Recommended correction, preserving the contract

Do not silently reinterpret `recorded_at` or remove its existing meaning. A safe follow-up should:

1. Use server `received_at` for the two-minute ingestion-recency filter and latest-point ordering.
2. Continue returning the original device `recorded_at` as capture time.
3. Expose `received_at` as a separate field in a versioned or compatibility-reviewed RPC response, so the dispatcher UI can distinguish recent receipt from old capture.
4. Label a point stale when the capture time is too old or implausibly ahead, even if it was recently received.
5. Preserve the existing assignment/incident `en_route` checks, dispatcher-only authorization, coordinate validation, and bounded result set.
6. Review Android and web consumers before changing the return shape; do not break clients that deserialize the current six-column table result.
7. Add tests for clock-behind, clock-ahead, delayed delivery, legacy rows with NULL `received_at`, and a unit leaving `en_route`.

A client-supplied capture time should never be treated as proof of physical presence or as a trusted security timestamp.

## Additional privacy and operational safeguards

- Keep exact responder coordinates out of general Admin audit logs and aggregate analytics.
- Restrict live coordinate access to dispatch workflows that need it; do not broaden access to all Admin accounts by convenience.
- Keep the two-minute live-map window bounded and explicit in UI copy; distinguish no recent location from no active assignment.
- Avoid logging coordinate values in telemetry, errors, or request bodies.
- Ensure any future location observability records only metadata and cannot delay SOS creation, assignment, status updates, or GPS writes.
- Verify live RLS policies and function grants before claiming the deployed project matches the repository.
