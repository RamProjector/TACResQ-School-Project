# TACResQ Incident Claiming — Implementation Plan

## Feature purpose

TACResQ will provide an incident-claiming workflow that allows eligible on-duty responders and drivers to take responsibility for an incident that the dispatcher has made available for field claiming. This gives field units a clear way to volunteer for an available response while preserving the dispatcher's authority to manage the incident queue, coordinate the response group, and intervene when operational circumstances change.

A successful claim will create or confirm the authenticated field unit's assignment to the incident through the existing assignment model. It will not create a new user role, appoint a team leader, bypass duty eligibility, or treat the legacy incident-level `assigned_to` field as the source of truth. The existing response-group model will be retained, including the limit of up to five eligible responders/drivers per incident and each member's independent status history.

## Intended workflow

The dispatcher will be able to make an eligible incident available for field claiming through the existing dashboard workflow. Only an incident explicitly marked as claimable and in an allowed open state will appear in the responder/driver claim list. A field unit must be authenticated, have the responder or driver role, and be on duty before the claim action is enabled. The claim screen will show only the incident information that the signed-in role is authorized to view and will provide a clear action to claim the incident.

When a field unit submits a claim, TACResQ will send the request to a server-authoritative operation. The server will re-check the user's role and duty state, the incident's claimable and operational status, existing assignments, and the response-group capacity at the time of the operation. The claim will be committed as one atomic database transaction so simultaneous attempts cannot create duplicate membership for the same field unit or exceed the five-member limit. A successful response will update the field unit's current assignment view and will use the existing per-assignment status progression. A failed or stale request will return a safe, actionable result and refresh the available-incident list.

The dispatcher will retain visibility of all assignments created through field claims. The dispatcher will be able to continue coordinating the group, assign additional eligible units when capacity remains, and use the existing authorized reassignment or removal workflow where applicable. Claiming will not appoint a team leader or change who has authority to make dispatch decisions. Requesters will continue to see the incident status and the appropriate response information through their existing role-specific views.

## Claim eligibility and business rules

The initial implementation will use dispatcher-controlled claim availability rather than exposing every new incident automatically. This keeps field claiming within the existing dispatch process and allows the dispatcher to decide which incidents are appropriate for self-selection. The implementation will first inspect the current incident statuses, assignment rows, dashboard actions, and Supabase constraints before choosing the exact stored representation for claim availability. The chosen representation must be server-validated and auditable; a client-only visibility flag is not sufficient.

A claim may be accepted only when the authenticated profile is an eligible responder or driver, the field unit is on duty, the incident is in an allowed claimable state, and the incident has not been cancelled, completed, or otherwise closed. A field unit may not claim the same incident more than once. A user who already has an active assignment to the incident will receive an idempotent or already-assigned result rather than a second assignment row. A claim will be rejected when the response group has reached the existing maximum of five members. The same incident may continue to contain multiple individually accountable responders/drivers, consistent with the existing group-assignment model.

The feature will not use a GPS coordinate as proof of eligibility or automatically select the nearest responder. Location-based eligibility would introduce additional privacy, freshness, and fairness rules and should be assessed as a separate product decision. Claiming must remain available without granting the client broader access to responder locations or incident records.

## Backend and database design

The implementation will follow the repository's existing Supabase RPC and privilege model. A narrowly scoped authenticated RPC, provisionally named `api_claim_incident`, will perform the complete claim operation. The function will resolve the caller from `auth.uid()`, verify role and duty status from trusted profile data, lock the target incident row for the duration of the decision, validate claim availability and incident state, check current assignment membership and capacity, and insert the assignment using the existing assignment schema. The final SQL name and parameter contract will be selected after reviewing the current migrations and callers.

The operation must be atomic. The design will use transaction-scoped locking and/or appropriate uniqueness constraints to protect the incident membership and capacity checks under concurrent requests. It will not implement a client-side read-then-insert sequence. The RPC will return a small set of explicit outcomes such as claimed, already assigned, not claimable, incident unavailable, off duty, role not allowed, group full, and not found. Responses for unauthorized or nonexistent incidents will avoid disclosing sensitive incident details.

The RPC will use a fixed safe search path and explicit caller authorization. Direct client table writes will remain restricted according to the current privilege model; authenticated users will receive execute permission only for the narrowly scoped operation. The migration will include the required grants and revoke statements, and the RPC-grant contract and clean PostgreSQL migration replay will be updated. Existing assignment transition RPCs remain the authoritative way to move an assigned member through the response lifecycle.

The claim operation will reuse the existing assignment notification and persistent inbox mechanisms where their current event contracts support it. A successful claim must not produce duplicate notifications if the client retries after a timeout or receives the same successful response twice. The server transaction and notification event design will establish a single authoritative outcome. Notifications will contain only the minimum information needed to direct recipients back to TACResQ; authorized incident details will be fetched after the app opens.

## Android client and dispatcher dashboard

The Android app will provide a claimable-incidents view for eligible responder and driver accounts. The view will distinguish loading, available, empty, offline, stale, and error states rather than showing an empty list when a request fails. Each incident card will present the approved summary information and a clear claim action. Before submission, the app will prevent repeated taps while a claim is in flight, show the server's confirmed result, and refresh the list after success or a conflict. If another field unit claims the final available slot first, the user will see a clear explanation that the response group is full or the incident is no longer available.

After a successful claim, the incident will appear in the user's assigned-work area and use the existing assignment-specific status actions, chat, map, and routing boundaries. The client will not optimistically grant access to protected incident content based only on a button tap or locally cached list entry. It will refresh through authenticated repository operations before showing sensitive details. Sign-out, account switching, duty changes, incident closure, and loss of assignment must invalidate or refresh claim-related UI state.

The TACRU dispatcher dashboard will expose the claimable state through an explicit dispatch action and clearly distinguish dispatcher-assigned members from field-claimed members where that distinction is operationally useful. The queue and member details will continue to show each member's own assignment status and update time. Claiming will not change the meaning of the existing team summary count, create a leader field, or silently rewrite incident-level aggregate status.

## Implementation sequence

The first phase will audit the current schema and code paths. It will inspect the incident status values, `incident_assignments` constraints and indexes, profile role/duty fields, existing assignment RPCs, notification triggers, dashboard assignment controls, and Android assigned-work repositories. The result will be a short schema contract for claim availability, response outcomes, and authorization boundaries. This phase will identify any overlap with existing assignment operations before adding new SQL or UI.

The second phase will implement the database operation and its tests. The migration will add only the minimal claimability representation and atomic RPC required by the audited schema. It will include caller identity checks, role and duty verification, allowed incident-state checks, duplicate prevention, response-group capacity enforcement, fixed search path, and least-privilege grants. Clean PostgreSQL replay and SQL/runtime tests will cover an eligible responder, eligible driver, requester denial, dispatcher-only visibility rules, off-duty denial, closed or cancelled incidents, repeated claims, group-capacity boundaries, revoked or changed eligibility, and concurrent claims against the same incident.

The third phase will integrate Android. The repository/API layer will expose typed claim outcomes rather than raw database messages. The ViewModel will manage loading and in-flight state, refresh the claimable queue on lifecycle return, and reconcile ambiguous network failures by fetching the caller's current assignment before offering a retry. The UI will provide accessible claim actions, progress feedback, and safe empty/error/conflict states. Unit and source-contract tests will cover role gating, double taps, retry behavior, stale entries, and post-claim navigation.

The fourth phase will integrate the dispatcher dashboard and notifications. Dispatchers will be able to mark an eligible incident claimable and see field claims in the existing response group. The implementation will preserve manual assignment and current authorization boundaries. The notification layer will be checked for one authoritative event per successful assignment and will not generate duplicate alerts during retries.

The fifth phase will complete end-to-end regression and operational review. Synthetic accounts will exercise the requester-to-dispatcher-to-responder/driver journey, including dispatcher enabling and withdrawing claim availability, two field units competing for the final slot, a claim followed by status progression, a field unit going off duty, incident cancellation/closure, and sign-out/account switching. Tests will confirm that existing dispatcher assignment, the five-member group limit, independent member statuses, GPS visibility rules, incident chat, map navigation, and notifications remain intact.

## Acceptance criteria

The feature will be accepted when an authorized dispatcher can explicitly make an eligible incident claimable; only authenticated on-duty responders and drivers can claim it; the server commits assignment membership atomically; duplicate submissions are idempotent; concurrent submissions cannot exceed the existing five-member capacity; and every successful claim appears consistently in Android and the dispatcher dashboard. A successful claim must continue through the existing assignment-specific status progression without creating a team leader or changing the authority model. Unauthorized, off-duty, stale, closed, cancelled, and full-group attempts must fail safely without leaking incident details or creating partial assignment records.

The change must pass the repository's required source checks, Android debug builds, JVM tests, debug lint, instrumentation-test compilation, migration-history alignment, clean PostgreSQL replay, RPC-grant contracts, Laravel/dashboard integration, repository security guardrails, and applicable CodeQL checks on the exact final commit. Browser, emulator, or physical-device testing will be reported separately from compilation and source contracts. No live Supabase migration, Render deployment, production setting change, or live incident mutation is included in the implementation plan; those actions require separate review and explicit authorization.

## Repository touchpoints

The implementation will be based on the existing Android repository and role-navigation structure under `app/src/main/java/com/tacresq/app/`, the current Supabase migrations under `supabase/migrations/`, server-side RPC/notification behavior, the TACRU dashboard under `backend/web/`, and the existing contract and integration tests under `tools/`. The exact files will be selected after tracing the current assignment operation end to end. Existing dispatcher assignment and status-transition behavior will be preserved; the claim feature will extend that workflow rather than replace it.

## Scope boundary

The first release is a dispatcher-controlled, authenticated field-claim workflow for the existing responder and driver roles. It does not add public incident self-assignment by requesters, unverified location-based dispatch, automatic nearest-unit selection, a new leader role, or direct client writes to assignment tables. More advanced policies such as jurisdiction rules, qualification matching, response-area restrictions, and automatic assignment can be evaluated separately after the basic claim workflow is validated with TACRU's approved operating procedures.
